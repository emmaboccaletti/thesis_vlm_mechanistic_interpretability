## Language Counterfactual Design

The agreed design is:

- Perturb only transcript text.
- Never modify the fixed prefix: `You are watching a football match.`
- Never modify the fixed question: `Is this a goal? Answer yes or no.`
- Do not require POS matching in the first implementation.
- Select a configurable fraction of eligible transcript words.
- Replace each selected source word with a different word from the same exact Qwen token-length bucket.
- Preserve the total tokenized length of the complete prompt.
- Use deterministic sampling based on stable sample identifiers and token positions.

For now, an eligible word is a transcript token that:

- is not whitespace;
- is not punctuation;
- contains alphabetic characters;
- has at least one different replacement in the corresponding tokenizer-length bucket.

POS filtering, named-entity filtering, and semantic compatibility remain optional future refinements rather than current requirements.

The replacement algorithm now works as follows:

1. Parse the transcript with spaCy.
2. Exclude whitespace, punctuation, and non-alphabetic tokens.
3. Measure each source word with the Qwen tokenizer.
4. Look up replacements from the same token-length bucket.
5. Rank source tokens deterministically using the task, sample ID, token offset, and source text.
6. Compute the target number of changes as `ceil(number_of_eligible_words * perturbation_fraction)`, with at least one replacement when eligible words exist.
7. For each candidate, sample a different same-length replacement.
8. Apply the candidate together with already accepted replacements.
9. Re-tokenize the complete prompt, including the fixed prefix and fixed question.
10. Accept the candidate only if the complete prompt length remains unchanged.
11. Continue until the target count is reached or no further safe replacements exist.
12. Return the safely perturbed transcript and audit metadata.

The requested perturbation percentage is therefore a target. If tokenizer context prevents the full target from being reached, the builder returns the largest safe deterministic subset rather than producing an invalid counterfactual.

## Same-Token-Length Vocabulary Lifecycle

The replacement buckets are built from the complete set of clean MOMENTS transcript records, not from each individual input sentence.

For every clean record, the builder scans both `local_text` and `global_text`. It identifies eligible word-like spaCy tokens, measures each word with the selected Qwen tokenizer, and groups the words by exact tokenizer length:

```text
1-token bucket: [...]
2-token bucket: [...]
3-token bucket: [...]
```

The exact bucket contents depend on the MOMENTS transcripts and the tokenizer version/model path. A source word can only be replaced by a word from the bucket with the same Qwen token count.

### First dataset-generation run

When the dataset builder is run in `dataset_sample` mode, it checks for a vocabulary cache. The default cache path is:

```text
<output_dir>/moments_<task>/qwen_same_token_length_vocab.json
```

If this cache does not exist, the builder:

1. loads the Qwen tokenizer;
2. scans all clean MOMENTS records;
3. tokenizes every eligible transcript word;
4. creates the exact-length buckets;
5. sorts the words for deterministic ordering;
6. saves the vocabulary and tokenizer path to the JSON cache;
7. uses the buckets to generate the language counterfactual CSVs.

### Subsequent dataset-generation runs

The buckets are not rebuilt for every sentence, replacement, or experiment example. On later runs, the builder loads the existing JSON cache if:

- the cache file exists; and
- the cached `tokenizer_path` matches the tokenizer path requested for the current run.

The cached buckets are then reused to generate new CSVs, for example when changing the perturbation fraction or regenerating a different counterfactual mode.

Conceptually:

```text
First run:
transcripts -> build buckets -> save JSON -> generate CSVs

Later runs:
load JSON buckets -> generate CSVs
```

### When to rebuild the cache

The current cache check detects a tokenizer-path change, but it does not automatically detect changes to the transcript dataset. Therefore, rebuild the cache or provide a new cache path if:

- transcript files are added, removed, or edited;
- the annotation subset changes substantially;
- the tokenizer or model version changes;
- tokenizer configuration changes;
- the experiment needs a fresh vocabulary snapshot.

The cache can be deliberately regenerated by deleting the old JSON or passing a new `--language_vocab_path`.

### Reproducibility requirement

The vocabulary cache is part of the experiment provenance. It should be generated on Snellius with the exact tokenizer used by the Qwen experiment, for example:

```bash
--language_tokenizer_path /home/eboccaletti/models/qwen2vl7b
```

The resulting `qwen_same_token_length_vocab.json` should be retained alongside the generated MOMENTS CSVs. This records which replacement pool was used and prevents later runs from silently using a different tokenizer or transcript vocabulary.
